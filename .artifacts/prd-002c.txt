## Technical Requirements
- **TR-1** Key source: MICHAEL_ENCRYPTION_KEY (64 hex = 32 bytes) from the host .env is the only master key; the module never falls back to .leo-keys and never generates a key — VALIDATION b4ed3c2c measured encryption.cjs generating a different throwaway key on a missing key file and failing GCM authentication on read-back; a consent from a worktree or GHA would encrypt the chairman's refresh token unrecoverably while reporting success. Spec section 4 venue paragraph: the master key lives in the host .env and nowhere else.
- **TR-2** Every michael_credentials read and write goes through lib/michael/db.mjs readRows/writeRows so a missing relation surfaces as TABLES_ABSENT, not a throw — The -B migration is chairman-gated and unapplied; the Supabase client factory throws on schema drift (VALIDATION condition 2). The consent script must refuse before the browser opens.
- **TR-3** Host-venue guard: any process with GITHUB_ACTIONS=true or CI=true is refused before decrypt and before consent — Ratification ff4ef5b4 / 0daf3bd8: credentialed feeders run on Windows Task Scheduler on the host; GHA holds no user credential and no encryption key. The guard makes the venue a code invariant, not a workflow convention.
- **TR-4** Fingerprint: first 16 hex of sha256 over the raw key bytes, stamped on every write and compared on every read before decrypt; mismatch is a named refusal — encryption.cjs decrypt ignores its metadata argument, so a wrong key is indistinguishable from corruption (Explore gap 3). The fingerprint leaks nothing about the key and makes a rotated or wrong host key diagnosable in one line.
- **TR-5** Import-time purity for lib/michael/gmail-client.mjs and chairman-oauth.js: no env read, no client construction, no network at module load — gmail-act.mjs's lazy loader re-throws anything that is not module-not-found, so an import-time throw becomes exit 1 rather than the designed exit-2 refusal.
- **TR-6** Tests are *.test.js (not .test.mjs) under lib/integrations/google/, lib/michael/ and server/routes/ so the vitest unit project collects them; they inject sb/enc/gmail factories and use real AES-256-GCM in at least one case — vitest.config.js:288-303 collects **/*.test.js only; the .mjs includes are anchored to two unrelated folders. The oauth-manager.test.js algorithm-pin rationale (a random-nonce fake satisfies every other assertion) applies here.
- **TR-7** The YouTube module and the chairman module share GOOGLE_CLIENT_ID and port 3456 but keep separate storage (eva_sync_state vs michael_credentials) and separate app ids; the two consent flows are never run concurrently — VALIDATION coordination note; a shared port cannot serve two callbacks at once, and cross-writing storage would let one flow clobber the other's grant.

## Architecture
A thin generalization of the YouTube OAuth manager into a host-only Google chairman-grant module. The module owns the key source (env-bound HostKeyEncryption), the venue guard, the ciphertext-only storage in michael_credentials, and token refresh with gauge predicates written as columns. Two consumers sit on top: the consent CLI (the re-consent runbook) and the Gmail modify client that child B's gmail-act verb already lazily imports. A read-only status route exposes non-secret columns behind requireAuth for child G's gauge and child H's dashboard.

Data flow: Consent: google-consent.mjs -> assertHostVenue -> key/env/table pre-flights -> generateAuthUrl (gmail.modify, calendar.readonly, drive.readonly) -> browser -> localhost:3456/oauth2callback -> getToken -> storeTokens: enc.encrypt(tokens) -> upsert michael_credentials {encrypted_blob, encryption_metadata, key_fingerprint, scopes, expires_at, last_refreshed_at, last_error:null}. Use: gmail-client.modifyThread -> getAuthenticatedClient -> getStoredTokens: readRows -> fingerprint compare -> enc.decrypt -> setCredentials -> refresh if expired (success: storeTokens; invalid_grant: last_error='invalid_grant' then rethrow) -> gmail.users.threads.modify -> { ok, modified } -> gmail-act records michael_gmail_triage_items. Observe: GET /api/michael/oauth/status (requireAuth) -> select non-secret columns -> hours_to_expiry; child G's michael-oauth-health reads last_error and expires_at directly from the table.

- **TS-4** (unit) invalid_grant is recorded for the gauge: given a stored expired token and an OAuth2 client whose refreshAccessToken rejects with an error containing invalid_grant; when getAuthenticatedClient runs; then the row update sets last_error='invalid_grant', the blob is untouched, and the call rejects

## Acceptance Criteria
- No plaintext token is ever written to michael_credentials: every write carries encrypted_blob and encryption_metadata, no token property becomes a column, and a unit test with real AES-256-GCM proves the fixture strings are absent from the payload
- The master key comes only from MICHAEL_ENCRYPTION_KEY: missing or malformed values are named refusals, no key is ever generated, and key_fingerprint is stamped on write and compared before decrypt with KEY_FINGERPRINT_MISMATCH on difference
- GITHUB_ACTIONS=true or CI=true refuses with HOST_VENUE_REQUIRED before any decrypt or consent, and no workflow references MICHAEL_ENCRYPTION_KEY, GOOGLE_CLIENT_ID or GOOGLE_CLIENT_SECRET
- node scripts/michael/google-consent.mjs is the whole re-consent runbook; it refuses TABLES_ABSENT before opening the browser while the -B migration is unapplied; --status shows non-secret columns only
- gmail-act --dry-run no longer refuses GMAIL_CLIENT_ABSENT; modifyThread maps to gmail.users.threads.modify and returns { ok, modified } or { ok:false, error }
- server/index.js mounts /api/michael with requireAuth on the same line, proven by a test that reads the mount table; /oauth/status returns no blob fields
- A SECURITY sub_agent_execution_results row with content_hash, session_id and evaluated_commit_sha exists for phase EXEC before EXEC-TO-PLAN; the diff contains no migration

## Risks
- A consent completed while michael_credentials is unapplied would burn a chairman grant with nothing persisted (MEDIUM/HIGH): google-consent.mjs pre-flights the table via readRows and refuses TABLES_ABSENT before generateAuthUrl; unit test TS-7 pins the order; rollback: Re-run the consent after the chairman applies the -B migration; Google issues a fresh refresh token on prompt=consent
- The seven-day refresh-token expiry (Testing-status consent screen) makes the grant lapse silently (HIGH/MEDIUM): expires_at and last_error are written by the module on every refresh so child G's michael-oauth-health trips on invalid_grant or <48h; the runbook is one host command; rollback: Run node scripts/michael/google-consent.mjs on the host; feeders treat invalid_grant as status failed until then
- A wrong or rotated MICHAEL_ENCRYPTION_KEY on the host renders the blob unreadable and looks like corruption (LOW/MEDIUM): key_fingerprint compared before decrypt yields KEY_FINGERPRINT_MISMATCH naming the cause; --status prints the stored fingerprint; rollback: Restore the original key in the host .env, or re-consent under the new key (storeTokens overwrites the row)
- Port 3456 collision with the YouTube consent flow or a stale listener (LOW/LOW): Documented as never-concurrent (TR-7); the callback server closes on the first code/error and times out at 5 minutes; rollback: Kill the stale listener and re-run the consent
- The requireAuth mount regresses to optionalAuth or is dropped in a later edit and the repo audit does not notice a GET-only route (LOW/HIGH): server/routes/michael.test.js reads server/index.js and asserts the /api/michael mount line contains requireAuth; rollback: Revert the mount line; the route file itself never decrypts so exposure is limited to non-secret columns

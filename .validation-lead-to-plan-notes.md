## 3. CAVEAT A (BLOCKING for the PRD) — preserve and reclaim cannot both happen in one tick

**This is the highest-value finding.** FR-4's P1 requires the slot freed "within one tick". As the
code stands that is impossible, because PRESERVE defeats the reclaim guard by doing its job.

The removal path (`scripts/worktree-reaper.mjs:1707`) consults:

```js
const treeResidency = treeResidencyBlocksRemoval(wtPath, { ... });
```

and `decideRemoval` (line 1723) treats it as a hard veto ("Every guard is still a veto EXCEPT the
claim guard's `work_key_unresolvable`").

`treeResidencyBlocksRemoval` (`lib/worktree-reaper/residency-guard.js:222-292`) computes
`Math.max(mtimeMs, headMs)` and blocks when that is younger than `DEFAULT_RESIDENCY_WINDOW_MIN = 30`
minutes (240 for trees outside `.worktrees/`).

PRESERVE, as FR-1 specifies it, does `git add -u` → `git commit` → `git push`. That sets **both**
inputs to now: HEAD is a brand-new commit, and the working directory mtime is fresh. So the tree
reads as `REAP_BLOCKED_TREE_RESIDENT` for the next 30 minutes — caused entirely by the reaper's own
preserve step. This is not hypothetical: `REAP_BLOCKED_TREE_RESIDENT` appears 287 times in
`.claude/worktree-reaper-last.log`; the guard fires constantly.

**The PRD must choose and state one:**

- **(a) Narrow exemption (recommended).** Skip `treeResidencyBlocksRemoval` for a tree whose preserve
  ref is verified on origin for the current HEAD. Justification is principled, not a workaround: the
  guard exists to prevent *content loss* from deleting an occupied tree, and a verified push to
  origin makes content loss impossible. Must be narrow — keyed on *this run's verified preserve
  pointer*, never on "recently touched by anything".
- **(b) Two-tick design.** Preserve on tick N, reclaim on tick N+1 once the residency window has
  aged out. Safer, but then **FR-4's P1 acceptance text must change** from "within one tick" to
  "within two consecutive ticks", and the CI test must drive two ticks with a clock injection.

Either way the PRD must state it explicitly. If it does not, EXEC will ship a P1 test that can only
pass by disabling the guard — which is the failure shape this SD family exists to prevent.

## 4. CAVEAT B (BLOCKING for the PRD) — Correction (2)'s stated root cause does not match the code

The SD's Correction (2) says:

> scripts/safe-worktree-remove.mjs WITHOUT --force refused all nine shipped trees; specimen
> decision=skip reason=live_owner owner_session=null heartbeat_age_s=null. **The current guard reads
> a NULL owner as LIVE (fail-closed)** ... FR-1's reclaim predicate must read a null owner as NO
> OWNER.

**The observed symptom is real. The stated mechanism is not.** Traced:

1. `owner_session` and `heartbeat_age_s` come from `logReapDecision`
   (`lib/worktree-reapability.js:301`), where they are **optional parameters defaulting to `null`**.
2. Its only caller on this path, `removeWorktreeViaGit` (`lib/worktree-manager.js:1544`), passes
   `{ worktree, decision, reason }` and **never passes them at all**.
3. So `owner_session=null heartbeat_age_s=null` is a **logging artifact** — it is not evidence that
   any owner field was read as null. There is no null-owner branch to fix.
4. `isReapable` (`worktree-reapability.js:263`) takes `liveOwner` as a plain **boolean input**.
   `Boolean(null)` is `false`, so a null claim would return NOT-live.

The actual mechanism that produces `live_owner` on a dead-owner tree is in
`safe-worktree-remove.mjs:53-71`, and it is a *different bug with a different fix*:

```js
return Boolean(data?.claiming_session_id);
```

`resolveLiveClaim` treats **presence of a claim row value as liveness** and performs **no liveness
probe of any kind** — no PID check, no heartbeat, no tool clock. A session that died in the morning
restart without releasing still has `claiming_session_id` populated, so its tree reads `live_owner`
forever. That matches the SD's own description ("every pre-10:12Z session died in the morning
restart") and fully explains freed-count = 0.

Secondary contributors on the same function, both of which also yield `liveOwner=true`:
- missing `SUPABASE_URL`/key → `return true` (line 59)
- any query error → `return true` (line 68)
- for QF keys it queries `quick_fixes` with `idColumn='id'` (line 65) — if that lookup ever errors,
  every QF tree fails closed to live.

**Consequence for the PRD**: the remedy FR-1 already prescribes (marker-union PID check + tool-clock
freeze) is **correct and would fix this**. Only the *stated root cause* is wrong. Write the PRD
against the real mechanism — "claim-row presence is used as a liveness proxy with no liveness
probe" — not against "null reads as live", or EXEC will go looking for a null branch that does not
exist and will conclude the bug is already fixed.

**Related sub-claim, also imprecise**: "treats any dirty file as unpushed work". `isReapable` keeps
`dirty_tree` and `unpushed` as separate reasons with separate precedence (lines 266-269). And
`collectDirtyStatus` runs `git status --porcelain --untracked-files=all`, which does **not** list
gitignored files. So the FR-1 distinction the SD asks for is really **dirty-tracked vs
untracked-but-not-ignored** (scratch files, `.artifacts/`, one-off scripts). Ignored files are
already excluded by construction — which is consistent with FR-1's own "ignored files (.env
snapshots) are excluded by construction".

## 12. FR-4 test infrastructure — feasible, with one hard constraint

Precedent exists: `tests/unit/fleet/source-tree-identity-realgit.test.js` builds a real-git fixture
with a bare repo, and ~10 tests under `tests/unit/fleet/` and `tests/unit/worktree-reaper/` create
real `git worktree add` fixtures. `tests/unit/worktree-reaper/audit-sink.test.js` already exists and

**Hard constraint the PRD must state**: P1 must push to a **local bare-repo fixture used as
